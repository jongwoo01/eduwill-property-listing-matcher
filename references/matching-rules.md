# 조건 해석과 순위

## 목차

- 목적 확인
- 하드·소프트 판단
- 미확인값 처리
- 순위와 0건 처리
- 출력 규칙

## 목적 확인

실거주인지 투자인지가 불분명하고 결과 순위에 영향을 주면 먼저 묻는다. 실거주 검색에 수익률을 임의로 끼우지 않고,
투자 검색에서는 향·층의 비중을 자동으로 높이지 않는다.

## 하드·소프트 판단

필드 이름이 아니라 손님의 표현으로 판단한다.

- 하드: “반드시”, “이상”, “이하”, “안 돼요”, “꼭 필요”처럼 불충족 시 제외해야 하는 조건
- 소프트: “좋겠어요”, “선호”, “가능하면”처럼 순위에만 반영할 조건

예산·거래유형·종류는 대개 하드다. 면적·역거리·향·층도 명확한 상한·하한이 있으면 하드가 된다. “넓은 집”,
“역세권”, “신축”처럼 기준이 모호하면 기준을 되묻거나 적용 기준을 밝힌다.

자연어를 `tool-usage.md`의 조건 JSON으로 바꾼다. 지역은 `지역(시군구)`과 `동네(읍면동)`를 구분하고,
특정 역은 `인근역`, 특정 초등학교는 `초등학교`로 비교한다. 스키마에 없는 감성 표현은 억지로 수치화하지 않는다.

## 미확인값 처리

하드 조건의 값이 `?`이면 일치로 판정하지 않는다.

- 모든 하드 조건 확인 완료: `matches`
- 하드 조건 일부가 `?`이고 명시적 불일치는 없음: `needs_verification`
- 하드 조건 하나라도 불일치: 제외

예를 들어 반려동물 필수가 `?`인 매물은 “가능 매물”이 아니라 “집주인 확인이 필요한 후보”다. 이 후보는 손님용
추천문에 바로 넣지 않는다.

## 순위와 0건 처리

1. 완료·보류 매물을 제외한다.
2. 하드 조건으로 일치·확인 필요·제외를 나눈다.
3. 소프트 조건 만족 개수가 많은 순으로 정렬한다.
4. 동점이면 거래유형에 맞는 가격이 낮은 순, 그다음 `접수일` 최신순으로 정렬한다.

보류 매물은 기본 검색에서 제외한다. 사용자가 보류 매물까지 명시적으로 요청한 경우에만 `--include-hold`로 다시 검색하고,
각 결과에 보류를 표시한다. `match_status_counts`와 `verification_status_counts`로 진행·보류 건수를 나눠 말한다.

실제 후보 결과에 거래유형이 둘 이상이면 조건 JSON에 `거래` 필드가 있더라도 유형별로 묶는다. 매매가·전세보증금·월세는
서로 같은 가격축이 아니므로 유형 사이의 순위를 만들지 않고 경고한다. 월세 안에서는 월세, 보증금 순으로 정렬한다.

검증된 결과가 0건이면 `search` 출력의 `relaxations`만 사용한다. 이는 조건 하나를 제외했을 때의 실제 건수다.
두 조건 이상을 함께 완화한 건수는 다시 검색해서 계산하기 전에는 말하지 않는다.

## 출력 규칙

사용자에게는 내부 JSON 이름 대신 쉬운 업무 표현을 사용한다.

- `matches` → `조건에 맞는 매물`
- `needs_verification` → `확인 필요`
- `relaxations` → `조건을 조정했을 때 찾을 수 있는 매물`

다음 순서를 사용한다.

1. `조건에 맞는 매물은 N건입니다`로 결론
2. 필수조건과 선호조건을 짧게 구분
3. 조건에 맞는 매물 최대 10건 — 상위 3건은 매칭 이유 표시
4. 사용자가 요청한 경우에만 확인 필요 후보 — 어떤 값을 확인해야 하는지 별도 표시
5. 0건이면 실제로 다시 계산한 조건 조정 선택지
6. 현재 결과에 맞는 다음 요청 예시 하나

완료 매물이나 `?`가 있는 필수 조건을 만족했다고 표현하지 않는다.

사용자가 손님용 문안을 요청하지 않았다면 검색 결과마다 자동으로 긴 문안을 붙이지 말고 다음 요청 예시로 제안한다.
요청받았을 때의 구조·표현 규칙과 예시는 `client-message.md`에 있다.

`search` 출력에 `warnings`가 있으면 결과와 함께 전달한다. 거래유형이 섞였다는 경고는 유형 간 가격 비교가
성립하지 않는다는 뜻이므로, 전체를 하나의 순위로 설명하지 말고 거래유형별로 나눠 보여준다.
